## Source and dependency review

The new ordinary logger keeps capability redaction, thread-local `logging::capture`, and recent Dev Toolbox lines on the calling thread. It queues records with nonblocking `try_send` into an 8192-message queue. A background writer batches writes, accounts for dropped records with a gap marker, and periodically calls sink sync. Logger-thread startup failure falls back to synchronous direct sinks. No Cargo/dependency/API update is required outside the five paths.

New `logging::drain(DRAIN_WAIT)` calls use a 500 ms bound for Rust panic, ordinary main exit, and the forced GPU-stall exit. The queue drain reports progress after sink `put` calls; periodic durability sync is separate. Native crashes do not wait. Tests included intact in the commit cover stalled/slow sinks, dropping markers, and thread ordering; no such tests were run in this review.

On the upstream-only sixteen-candidate base, ordinary `Tee`/flusher code is still the upstream design this patch replaces. The earlier microphone-close thread and the wgpu pin are independent: this commit changes neither their ownership nor voice transmission/GPU fence behavior. Newer upstream uninstall routing appears only as unchanged main-context in the patch, so it is not a prerequisite for adding the normal-end drain.

## Concrete host semantic conflicts

The fork's `logging.rs` has a controller-specific contract absent from upstream:

1. `prepare_host_log` creates a distinct PID/nonce log and synchronously writes, flushes and syncs its unfiltered startup record before console detachment. `init_host` uses checked logger installation and can refuse startup. Its `Tee` has host error state and its flusher propagates sync failure into that state. Upstream replaces the surrounding `Tee`/initializer/flusher model with `Queued`/`Direct` sinks and has no adapter for this contract.
2. Upstream `LogSink::put` and `LogSink::sync` return no result; `LogFile` discards write/sync errors. In contrast, `HostState` latches lost-record errors and `HostLog::flush`/`sync` reports them to `session_host/startup.rs::run_checked`, which shows the controller-owned failure dialog. A mechanical selection of upstream sink semantics would lose that checked host error propagation.
3. Upstream `Tee::flush` becomes a no-op. Existing `HostLog::flush` first invokes the global logger flush and then syncs its retained file. Under an asynchronous queue this sequence does not prove pending records reached the file before that sync. Upstream's boolean `drain` acknowledges write attempts and bounded waiting; it does not provide the host's checked durable-flush result, and errors/timeouts cannot simply be ignored there.
4. The fork's `main` returns directly through `session_host::startup::run()` for the controller, before the ordinary main-exit drain added by upstream. Controller final result/error logging is handled by `run_checked` and its diagnostics guard, so the new normal-viewer drain call alone does not cover host shutdown or console-detachment failures.

Relevant exact fork paths: `crates/aurora-viewer/src/logging.rs`, `src/session_host/startup.rs`, and `src/main.rs`. These are reasons to defer intact import, not proposed conflict resolutions. Adapting checked queue acknowledgement, sink error propagation, durable startup/exit, panic behavior and host-owned console lifetime would be outside this read-only screen and intact-import allowance, and would require regression coverage.

No native chat bootstrap/profile/worker/UI source changes occur in this commit. Frozen `32b29839`'s terminal chat-authority revision fix stays untouched. This logging commit does not establish the cause of any earlier shutdown watchdog or driver issue.
